## Collaboration Protocol

**User-driven collaboration, not autonomous execution.**
Every task follows: **Question -> Options -> Decision -> Draft -> Approval**

- Agents MUST ask "May I write this to [filepath]?" before using Write/Edit tools
  (exempt: `active.md` appends, agent memory, a subagent's new file at the path
  its orchestrating skill named; see `.claude/rules/agent-memory.md`)
- Agents MUST show drafts or summaries before requesting approval
- Multi-file changes require explicit approval for the full changeset
- No commits without user instruction
- A skipped or dismissed question is not an answer: act on nothing, re-ask in
  plain text and wait
- Started outside this file's folder? Warn first: hooks, deny rules and the
  ask-first mode load only when Claude Code starts here

See `docs/COLLABORATIVE-DESIGN-PRINCIPLE.md` for full protocol and examples.

## What This Project Is

Two unrelated things share the name "Wulfram" — don't conflate them:

1. **Wulfram II (2002)** — the real, defunct game this whole effort is trying to revive. Built on a proprietary/custom engine, originated as "Shockforce" under Total Entertainment Network in the late 1990s, released independently by Bernt Habermeier's Slurpysoft in 2002. Predates Unity entirely. No source code exists anywhere; it's gone for good.
2. **This repo (`wulfram3`)** — a fan-made *recreation* of Wulfram II, built from scratch in Unity by a small community (2016–2018), unrelated technically to the original game's code. Got to "1.6 alpha" and stalled in January 2018. This is what we're reviving.

## Branch Model (set up and pushed to GitHub)

- **`master`** = prod. Stable, deployable, currently untouched at the original `21f284f` ("fixed size of gui", Jan 2018). Nothing merges here without explicit sign-off.
- **`dev`** = integration/testing. **First promoted 2026-10-16** (PR #14, merge `a17c31e`: M1, offline play, M2, regen fix, QA stage), then VERIFIED 17/17 on a fresh clone of `dev` itself. Playtest builds come from `dev`. Promotions after this one follow the runbook in "QA & Merge Process".
- **`revival/phase-0-1-bringup`** = active integration branch for the revival effort, pushed to origin. Feature branches (below) merge back into this one; this is what eventually merges into `dev`.

**Branch discipline and backtracking (user requirement, 2026-10-10: "keep all work organized into feature branches so we can backtrack with 1000% confidence"):**

- **Every piece of work gets its own `feature/<topic>` branch** cut from the current `revival/phase-0-1-bringup` head. No commits go directly on `revival/`, `dev` or `master`, docs included; doc follow-ups get a `docs/<topic>` branch and PR.
- **Commits are small and single-purpose**, each one revertable on its own: one fix, one tool, one doc update. Stage by explicit path (`git commit -- <paths>`) so an unrelated file can't ride along. A scene the editor marked dirty is the classic stowaway; if you didn't edit it, `git checkout -- <scene>`.
- **Merges are merge commits** (`gh pr merge --merge --match-head-commit <verified sha>`), never squash or rebase, and **feature branches are kept** after merging. Every commit stays reachable and is cited by SHA in this file.
- **Milestones get annotated tags** on the merge commit that landed them (`m1` → `3dd05cc`).
- **To backtrack:** undo a whole feature with `git revert -m 1 <merge commit>`, which leaves history intact and is itself revertable. Undo one piece with `git revert <commit>`. Look at an old state with `git checkout <tag or sha>`, or `git worktree add ../wulfram3-old <tag>` to open it in Unity side by side.

**Working style:** create branches/commit/edit files locally without asking each time. Confirm before pushing to GitHub or merging into `dev`/`master` — but push feature-branch work at reasonable checkpoints (not after every micro-edit) since "publish as we go" has been explicitly requested.

## QA & Merge Process (guardrails, set up 2026-08-29)

- **Branch protection on GitHub:** `master` and `dev` require a pull request — no direct pushes, no force-pushes, no branch deletion, and admins are NOT exempt — and the `checks` workflow must pass before merge. `revival/phase-0-1-bringup` and `feature/*` still accept direct pushes so day-to-day work stays fast; CI runs on every push there too, for early signal.
- **Automated checks — `.github/workflows/checks.yml`, every push and PR, no Unity license required:**
  1. *C# language-level guard* — fails on C# 6+ syntax this project's C# 4.0 compiler rejects (`?.`, `$"..."`/`$@"..."`, `nameof(`). This is exactly the bug class that broke the first real compile attempt (M1).
  2. *No UnityScript or Boo* (added 2026-10-07) — fails on any `.js`/`.boo` under `Assets/` (ignoring `.jslib` WebGL plugins and never-compiled folders). Unity 2017's legacy UnityScript compiler is unstable on the dev machine and caused corrupted builds; see "What's Already Fixed".
  3. *Unity script identity guard* (added 2026-10-07) — fails on UTF-16 `.cs` files and on MonoBehaviour/ScriptableObject classes whose name differs from the file name only by case. This is exactly the bug class behind the 17 missing Cargo scripts. Tested to fail on the original `cargo.cs`.
  4. *Unity `.meta` integrity* (added 2026-10-07) — fails if any tracked asset or folder under `Assets/` lacks a committed `.meta` (a fresh clone would invent a new GUID and break references), or if any `.meta` has no tracked asset. A folder counts only if it holds a real tracked file. Unity deletes such orphaned metas on first open, which is how the clean-room gate found 11 of them. Tested both ways.
  5. *Secret scan* — fails on any Discord webhook URL with a token anywhere in the tree.
  6. *Required scenes present* — `Assets/Scenes/Launcher 1.unity` and `Playground.unity` must exist.
  7. *Photon RPC check* (added 2026-10-16, `Tools/check-rpc.sh`; run it locally the same way) — every `[PunRPC]` method's parameters must be types PUN Classic can send (Photon protocol types, `Vector2/3`, `Quaternion`, `PhotonPlayer`, arrays of those, `PhotonMessageInfo`; no components, GameObjects, `ref`/`out`). Every `.RPC("Name", …)` must name an existing `[PunRPC]` method. Comments and strings are ignored, and `--list` prints everything it parsed. Known findings live in `Tools/rpc-baseline.txt`: a new finding fails, and so does a stale baseline line. It exists because PUN's offline mode doesn't serialize RPC arguments, so this bug class passes every offline test. It was tested on the 29 real methods and 29 call sites, plus a fixture of 15 cases (bad types, combined attribute lists, `[Obsolete("…(…)")]`, multi-line signatures, comments, strings) and the baseline rules.
- **Local gate — `Tools/verify-local.sh [--windowed] [--screenshots] [--editor] [--online]` (Git Bash, needs Unity 2017.3.0f3; covers what CI can't without a Unity license):** compile (fails on *any* `compilationhadfailure: True`), build-scene check (0 missing scripts), Cargo count (17), `WulframProjectAudit` compared with `Tools/audit-baseline.txt` (any new finding fails; fixed entries are reported for removal), a Windows player build (any "Script attached … missing" warning besides the known Tron 'Sun' one fails; that's the corrupted-build signature), and the offline smoke test headless (and windowed with `--windowed`, which also requires `probePanelShown=True`). The smoke test also runs through the launcher's real Play button with `-offlinePlay`. **Step 6e (since `feature/l1-gameplay-smoke`, 2026-10-20)** runs the L1 gameplay smoke test (`Assets/SmokeTest/GameplaySmokeTest.cs`, `-offlinePlay -gameplaySmokeTest`). It waits for the tank to settle, turns it to open ground through mouse-look's own yaw, fires `AutoCannon.TryFire` at a real enemy flak turret (AI off) held on the line of fire, and checks health, fuel spent, fuel regenerating, and destruction (unit removed, explosion spawned). It needs `GAMEPLAY: PASS`. With `--editor` it runs inside the **Unity editor's Play mode** as well, opened once on the launcher and once on Playground (`WulframEditorPlayCheck`); that needs PASS plus zero exceptions anywhere in the editor log, and opens the editor window for about 1–2 minutes per run. Smoke PASS requires `exceptions=0` **and** `errors=0`. In a working copy, the first compile after scripts are added or removed fails on Unity's stale script list and is rerun once, with a note in the output. It reads logs rather than exit codes and prints `VERIFIED` or `NOT VERIFIED`. Typical runtime is about 2 minutes on a warm Library and about 4–5 minutes for a fresh clone's first import. **Run it from an interactive desktop session.** The windowed player sometimes opens Unity's launch dialog first ("Wulfram 3 Configuration", the resolution/quality picker) and waits for **Play!**. For about an hour on 2026-10-07 that looked like a startup hang right after `<RI> Input initialized.`, until the window title gave it away. The dialog is a standard player option, and this project has it set to `Enabled` (`PlayerSettings.displayResolutionDialog`, printed by the audit), so real players see it on launch, as the original team configured. Why many *automated* launches skipped it is not known. `Tools/press-play.ps1` presses Play! the way a player would, by sending the button's command to the dialog (no mouse, keyboard or focus needed), and the script then requires a normal PASS. `--screenshots` saves the game's own rendered frames (launcher, arena, a 360° pan, panels) to `<out>/screenshots`. **Since `feature/qa-dev-stage` (2026-10-16):** every run saves its own report, `<out>/SUMMARY.txt` (date, commit, uncommitted-change count, flags, every step line, the verdict); copy the whole `<out>` minus `player/` into `qa-artifacts\gate-runs\<run>\` and add a row to `docs/QA-LOG.md`. `--stress N` runs steps 6, 6b and 6c N times each, every run with its own log (`-rK`) and PASS/FAIL line. In the online step the two clients run in **lockstep**: a barrier on a `smokePhase` player property, latched per actor so a client that reports and leaves in the same frame still counts. Each client's own verdict is printed, not only the shared-room check. Step 8 is rerun once, and noted in the output, only when its log shows Unity's license refresh forcing a script reload during Play; the rerun must pass.
- **Definition of "verified" before merging upward:**
  - `feature/*` → `revival/phase-0-1-bringup`: `checks` green **and** `Tools/verify-local.sh --windowed` prints `VERIFIED` on a **fresh clone of the exact commit being merged** (merge with `gh pr merge --merge --match-head-commit <sha>`, so nothing else slips in).
  - `revival/phase-0-1-bringup` → `dev`: all of the above **and** the milestone's own end-to-end proof (M1: opens/compiles/scenes clean; M2: two clients in one Photon room, damage lands both ways).
  - `dev` → `master`: `dev` has been exercised by real play (closed playtest, M3) with no open blockers.
- **Desktop etiquette: test runs must not take the owner's mouse, and must not outlive themselves** (owner rule, 2026-10-26, after a stopped gate kept launching game windows that pinned the mouse to the screen centre):
  1. **Ask the owner before any run that opens windows.** That means `--windowed`, `--screenshots` and `--editor` (step 7: a game window for about 30 s; step 8: the Unity editor twice, 1–2 min each). Those flags are opt-in, and the gate prints a NOTE before each such step. Headless steps (1–6e, the online pairs) open no windows and may run anytime.
  2. **Test runs release the mouse.** `OfflineSmokeTest` and `GameplaySmokeTest` unlock the cursor every frame. The game locks it to its window via `CursorVisibilityManager`; `Cursor.visible`, which the game's checks use, is left alone. The `SMOKE:` line reports `cursorReleased=True(Nx)`, and `-smokeLockCursor` restores the game's lock if a test ever needs it.
  3. **Nothing a run starts outlives it.** `verify-local.sh` calls `Tools/stop-gate-processes.ps1` on every exit (done, failed, interrupted) to stop its players, Unity runs and their child processes. Watchdogs stop the run if the shell that started it goes away. Tested: killing only the launching shell left nothing running after about 6 s.
  4. **Stop a gate with `Tools/stop-gate.sh`, never by stopping only the shell or task that started it.** It stops every test run on the machine, and never touches a playtest build under `builds\` or a Unity editor a gate didn't start (both tested).
- **Gate clones (2026-10-16):** clone into **`C:\Development\wulfram-gates\<name>`**, outside the VS Code workspace folder. The owner's VS Code has `git.autofetch: true` and started a second, full GitHub fetch into a gate clone inside the workspace one second after the clone began, doubling a 40-minute download. Clone from the local repo (`git clone --no-checkout --branch <b> --single-branch <local repo>`, sparse `'/*' '!/windows/'`), then check that `git rev-parse HEAD` equals `git ls-remote <GitHub> refs/heads/<b>`. Git commits are content hashes, so an equal SHA means identical content. Copy `<out>` minus `player/` to `qa-artifacts\gate-runs\<name>\`, add a QA-LOG row, and delete the clone.
- **Promotion runbook, revival → dev:**
  1. The revival head's tree must be identical to an already-verified feature head; otherwise run the gate on revival first.
  2. `gh pr create --base dev --head revival/phase-0-1-bringup`.
  3. Wait for **every** check run on the head SHA: the `push` run *and* the `pull_request` run. `gh pr checks --watch` can return after the first one; merging before both finish was refused once (2026-10-16) as "base branch policy prohibits the merge". Check with `gh api repos/<repo>/commits/<sha>/check-runs`.
  4. `gh pr merge --merge --match-head-commit <sha>`. Never `--admin`.
  5. Verify the `dev` tree equals revival and `dev` CI is green.
  6. Run the full gate (`--screenshots --editor --online --stress 3`) on a fresh clone of `dev`.
  7. Add the QA-LOG row and a docs PR.
- **Mechanics:** open a PR (`gh pr create`), wait for `checks` (every check run on the head SHA, see above), merge with a **merge commit** (`gh pr merge --merge`). Not squash or rebase: this file cites individual commit SHAs, and those must stay reachable. Keep feature branches after merging, for the same reason. A direct `git push` to `dev` or `master` is now rejected by GitHub; that is intentional.
