## What This Project Is

Two unrelated things share the name "Wulfram" — don't conflate them:

1. **Wulfram II (2002)** — the real, defunct game this whole effort is trying to revive. Built on a proprietary/custom engine, originated as "Shockforce" under Total Entertainment Network in the late 1990s, released independently by Bernt Habermeier's Slurpysoft in 2002. Predates Unity entirely. No source code exists anywhere; it's gone for good.
2. **This repo (`wulfram3`)** — a fan-made *recreation* of Wulfram II, built from scratch in Unity by a small community (2016–2018), unrelated technically to the original game's code. Got to "1.6 alpha" and stalled in January 2018. This is what we're reviving.

## Branch Model (set up and pushed to GitHub)

- **`master`** = prod. Stable, deployable, currently untouched at the original `21f284f` ("fixed size of gui", Jan 2018). Nothing merges here without explicit sign-off.
- **`dev`** = integration/testing. Still mirrors `master`. M1 is merged into `revival/phase-0-1-bringup` but not yet promoted to `dev`; that's the user's call.

**Branch discipline and backtracking (user requirement, 2026-10-10: "keep all work organized into feature branches so we can backtrack with 1000% confidence"):**

- **Every piece of work gets its own `feature/<topic>` branch** cut from the current `revival/phase-0-1-bringup` head. No commits go directly on `revival/`, `dev` or `master`, docs included; doc follow-ups get a `docs/<topic>` branch and PR.
- **Commits are small and single-purpose**, each one revertable on its own: one fix, one tool, one doc update. Stage by explicit path (`git commit -- <paths>`) so an unrelated file can't ride along. A scene the editor marked dirty is the classic stowaway; if you didn't edit it, `git checkout -- <scene>`.
- **Merges are merge commits** (`gh pr merge --merge --match-head-commit <verified sha>`), never squash or rebase, and **feature branches are kept** after merging. Every commit stays reachable and is cited by SHA in this file.
- **Milestones get annotated tags** on the merge commit that landed them (`m1` → `3dd05cc`).
- **To backtrack:** undo a whole feature with `git revert -m 1 <merge commit>`, which leaves history intact and is itself revertable. Undo one piece with `git revert <commit>`. Look at an old state with `git checkout <tag or sha>`, or `git worktree add ../wulfram3-old <tag>` to open it in Unity side by side.

**Working style:** create branches/commit/edit files locally without asking each time. Confirm before pushing to GitHub or merging into `dev`/`master` — but push feature-branch work at reasonable checkpoints (not after every micro-edit) since "publish as we go" has been explicitly requested.

## Playing and testing locally (no server needed)

Until M2 brings a working Photon server, normal play gets stuck: the launcher's Play button tries to connect to the dead 2017 server and sits on "Connecting…". **Offline play** (`feature/offline-play`) runs the whole game on one machine using PUN's offline mode:

- **Unity editor:** menu **Wulfram → Offline Play (no server)** toggles it (a check mark shows when it's on), then press Play. Or use **Wulfram → Play Offline From Launcher**. While it's on, Play always starts from the launcher scene (`EditorSceneManager.playModeStartScene`), whichever scene you have open, and stopping returns you to that scene. Starting directly in Playground can't work, because the game expects the launcher to have set up dependency injection, the player name and the room. In the game, click **Play** on the login screen; no username is needed, and you get a guest name. **Esc** toggles the mouse cursor: hidden means mouse-look and driving, visible means using the UI.
- **Built game:** `Wulfram3.exe -offlinePlay`, then press **Play!** on Unity's settings dialog, then Play on the login screen. A ready-made build with double-click `Play Wulfram (offline).bat` and `Play Wulfram (online).bat` is in `C:\Development\Wulfram_Development\builds\wulfram3-ac4b125\`, outside the repo.
- **The smoke test is not normal play.** Windows that appear for a few seconds and close by themselves are the automated smoke test (`-offlineSmokeTest`). It skips the login, runs the arena for `-smokeSeconds` (about 6–10s), checks targeting, leaves, and quits on purpose.
- The setting is per machine (EditorPrefs) and never committed. Chat is skipped while offline.
- **Online (M2, Photon Cloud):** with `Assets/Resources/PhotonAppId.local.txt` present, a normal Play (offline play **off**) connects to Photon Cloud. The first player creates a room and the next one joins it, blue team then red. Chat is off for now. To try two players on one machine, run the built game twice, a few seconds apart.

## What's Still Broken / Not Yet Done

- **RESOLVED 2026-10-07 — the 17 missing `Cargo` scripts and the "confirm Build Settings end to end" item.** See "What's Already Fixed" → session 2026-10-07. Short version: the scripts were never stale. `cargo.cs` was UTF-16 with a lowercase name, so Unity couldn't resolve it to a class. Fixing the file restored the original scene untouched, and a real build now boots Launcher → Playground cleanly. The detailed account of the old four-attempt CLI re-attach effort is in git history (`f9d2980` version of this file) if ever needed. Lesson worth keeping: when Unity reports a script as "missing" but the GUID still matches a real `.cs` file, check `MonoScript.GetClass()` (`WulframScriptCheck.CheckCargoScript`) before trying to re-attach anything.
- **SAM turret has no AI.** `RedBase/RML/Turret_SAM`'s original turret script was never committed anywhere (see "What's Already Fixed"). Its recovered field list is a spec for writing a replacement. Not an M1/M2 blocker. Any rewrite must be networked (master-client authority) to fit the RPC trust-model item below.
- **In-game chat is off** (2026-10-10). The chat UI's serialized App ID (on its `Chat` component) belongs to the original 2017 team, so this project must not use it, and online it logged "Cannot send op: 1 Not connected" on leaving. `ChatUIAutoLogin` now connects only when `Wulfram.Networking.PhotonCloudSettings.ChatEnabled` is true, which it isn't, and never when PUN is offline. To bring chat back: the user creates a second free Photon app of type **Chat**, and a branch loads its ID from a local file (like the PUN App ID), sets it on the `Chat` component, and flips the switch. While chat is off, the whole chat UI is hidden (PR #7), so no empty login box shows in the HUD.
- **Playground still opens "dirty" in the editor, but nothing rewrites it silently any more** (PR #9, merged 2026-10-10). The cause, found by diffing scenes with `WulframSceneDump`: on open, Unity's UI layout recomputes **layout-driven RectTransforms**, namely the TargetInfo panel rows, the game console text, and the chat dock and emoticons. The saved values differ, so the scene is marked dirty. The recomputed values aren't even stable (two re-saves disagreed on anchors and sizes), so committing a "recomputed" scene can't fix it. These values are driven at runtime and harmless to the game. Previously, the vendored **AutoSaver** saved the dirty scene whenever Play was pressed and every 2 minutes, so ordinary editor use modified `Playground.unity` in git. **AutoSaver is now off by default** (`AutoSaver.IsEnabled = false`), and an A/B test in the windowed editor showed no rewrites after 170s. Unity may still ask "save changes?" when you close the scene: answer **Don't Save** unless you actually edited it. You can turn AutoSaver back on per machine from its editor window, but the old behavior returns with it.
- **Editor-only warning: "The referenced script on this Behaviour (Game Object 'UpLink') is missing!"** appears when Playground plays in the editor. It comes from `BlueFiles/UpLink.prefab`, the prefab parent of the scene's UpLink, which is in the audit baseline with 1 missing script. Builds don't include that prefab, so players never see it. Worth its own branch to identify and remove, like the SAM turret.
- **Only the master client's own tank regenerates health** (found 2026-10-10 via a flaky M2 test). `HealthRegenerator.Update` (on the owner's client) calls `HitPointsManager.TakeDamage(-1)` directly, and `TakeDamage` only acts on the master client, so every other player's tank never heals. It should go through the master, e.g. `TellServerTakeDamage(-1)` from the owner, which also fits the RPC trust work below. Needs its own branch.
- **Target info panel disappears for good when its target leaves the screen** (pre-existing UX bug, found 2026-10-07). `TargetInfoController`'s `targetInfoPanel` *is its own GameObject*. When the target isn't visible, `LateUpdate` calls `SetActive(false)` on itself and stops running until the next target change. So the panel never comes back on its own when the target re-enters view, and it never shows at all if the target wasn't rendered in the frame before selection. The fix is to separate the panel from the controller (UI work, not a crash). Not done.
- **`PlayerMovementManager.FixedUpdate` calls `FindObjectOfType<TerrainCollider>()` every physics step**, which is wasteful; cache it. Pre-existing, not a correctness bug.
- **Scouts carry `DragTransform` (mouse-hover recolor + drag-with-mouse) on their `Lightning Emitter`.** It looks accidentally copied from the Procedural Examples lightning demo, but it's behavior, so it was kept exactly (just ported to C#). Decide during gameplay work whether to remove it. Note that no game code currently spawns `BlueScout`/`RedScout`; `GameManager` spawns only tanks.
- **`Resources/Terrains/Tron.prefab` ships in every build but nothing loads it.** It's in an `AstatineWars/Resources` folder and has a missing script on its `Sun` object; that's the one expected "Script attached to 'Sun' in scene ''" warning in every build log. Moving `AstatineWars` out of `Resources` would shrink the build.
- **Photon Chat logs one error when leaving Playground** ("Cannot send op: 1 Not connected. PeerState: Disconnected") as the chat client is torn down. Harmless; it goes with the M2 chat migration.
- **Unused legacy, harmless, not cleaned up:** `Assets/Scenes/Launcher.unity` + `Launcher.cs` (superseded by `Launcher 1.unity` / `LauncherWithLogin`); `Assets/Scenes/PlayerInputField.cs` (class `PlayerNameInputField`, a dead copy of a Photon tutorial script, referenced by nothing, with a file-name/class mismatch); `LauncherWithLogin.playername` field (unassigned, unused).
- **Photon networking: working (M2), with the App ID kept out of git.** The committed `PhotonServerSettings.asset` still says self-hosted `18.218.55.176` (dead), and it is deliberately **not** edited. At startup, `Assets/Networking/PhotonCloudSettings.cs` takes the App ID from `-photonAppId`, then `WULFRAM_PHOTON_APPID`, then **`Assets/Resources/PhotonAppId.local.txt`** (gitignored; the user's machine has it; it's baked into builds). It then switches an **in-memory copy** of the settings to Photon Cloud, region `us` (override with `-photonRegion`); changing the asset itself could be saved back by the editor or AutoSaver and leak the ID. CI fails if that local file is ever committed. **A fresh clone has no App ID**, so online play needs the file, or the variable, recreated. **Builds contain the App ID**, so share them privately; Photon's dashboard suggests adding authentication before any public release (M3). PUN Classic → PUN2 is no longer needed for M2. It's a later upgrade that requires Unity 2017.4.7+ first.
- **No real account/stats backend** — `OfflineMode` is a stopgap for local testing, not a long-term replacement for the dead `wulfram.com:1337` service. Current leaning: ship an accountless "quick play" mode first rather than building a replacement backend immediately.
- **SECURITY — leaked Discord webhook is still live in public git history; revocation is USER ACTION, not done yet.** The URL (with its auth token) was removed from `DiscordApi.cs` earlier, and on 2026-08-29 two more commented-out copies were found and scrubbed from `Assets/Scenes/Launcher.cs` and `LauncherWithLogin.cs` (caught by the new CI secret scan while testing it locally). But it has been in git history since 2017 — in this fork *and* in upstream `Wulfram3/wulfram3`, both public repos — so no tree cleanup or history rewrite fully un-leaks it. **The only real fix: revoke/delete that webhook in Discord (Server Settings → Integrations → Webhooks) and create a new one if the feature is wanted.** Until the user confirms this is done, treat the credential as compromised.
- **SECURITY — the original account backend used plaintext HTTP.** `UserController.cs` pointed at `http://wulfram.com:1337/` (not HTTPS): usernames/passwords would have crossed the wire unencrypted. Dead and bypassed now; any rebuilt backend must be HTTPS-only from day one.

Not a memory-safety issue (managed C#), but the real cheat vector for a revived multiplayer game. Needs a trust-model decision (master-client authority vs. validation) before any public playtest (M3) — not blocking M2.

## QA & Merge Process (guardrails, set up 2026-08-29)

- **Branch protection on GitHub:** `master` and `dev` require a pull request — no direct pushes, no force-pushes, no branch deletion, and admins are NOT exempt — and the `checks` workflow must pass before merge. `revival/phase-0-1-bringup` and `feature/*` still accept direct pushes so day-to-day work stays fast; CI runs on every push there too, for early signal.
- **Automated checks — `.github/workflows/checks.yml`, every push and PR, no Unity license required:**
  1. *C# language-level guard* — fails on C# 6+ syntax this project's C# 4.0 compiler rejects (`?.`, `$"..."`/`$@"..."`, `nameof(`). This is exactly the bug class that broke the first real compile attempt (M1).
  2. *No UnityScript or Boo* (added 2026-10-07) — fails on any `.js`/`.boo` under `Assets/` (ignoring `.jslib` WebGL plugins and never-compiled folders). Unity 2017's legacy UnityScript compiler is unstable on the dev machine and caused corrupted builds; see "What's Already Fixed".
  3. *Unity script identity guard* (added 2026-10-07) — fails on UTF-16 `.cs` files and on MonoBehaviour/ScriptableObject classes whose name differs from the file name only by case. This is exactly the bug class behind the 17 missing Cargo scripts. Tested to fail on the original `cargo.cs`.
  4. *Unity `.meta` integrity* (added 2026-10-07) — fails if any tracked asset or folder under `Assets/` lacks a committed `.meta` (a fresh clone would invent a new GUID and break references), or if any `.meta` has no tracked asset. A folder counts only if it holds a real tracked file. Unity deletes such orphaned metas on first open, which is how the clean-room gate found 11 of them. Tested both ways.
  5. *Secret scan* — fails on any Discord webhook URL with a token anywhere in the tree.
  6. *Required scenes present* — `Assets/Scenes/Launcher 1.unity` and `Playground.unity` must exist.
- **Local gate — `Tools/verify-local.sh [--windowed] [--screenshots] [--editor] [--online]` (Git Bash, needs Unity 2017.3.0f3; covers what CI can't without a Unity license):** compile (fails on *any* `compilationhadfailure: True`), build-scene check (0 missing scripts), Cargo count (17), `WulframProjectAudit` compared with `Tools/audit-baseline.txt` (any new finding fails; fixed entries are reported for removal), a Windows player build (any "Script attached … missing" warning besides the known Tron 'Sun' one fails; that's the corrupted-build signature), and the offline smoke test headless (and windowed with `--windowed`, which also requires `probePanelShown=True`). The smoke test also runs through the launcher's real Play button with `-offlinePlay`. With `--editor` it runs inside the **Unity editor's Play mode** as well, opened once on the launcher and once on Playground (`WulframEditorPlayCheck`); that needs PASS plus zero exceptions anywhere in the editor log, and opens the editor window for about 1–2 minutes per run. Smoke PASS requires `exceptions=0` **and** `errors=0`. In a working copy, the first compile after scripts are added or removed fails on Unity's stale script list and is rerun once, with a note in the output. It reads logs rather than exit codes and prints `VERIFIED` or `NOT VERIFIED`. Typical runtime is about 2 minutes on a warm Library and about 4–5 minutes for a fresh clone's first import. **Run it from an interactive desktop session.** The windowed player sometimes opens Unity's launch dialog first ("Wulfram 3 Configuration", the resolution/quality picker) and waits for **Play!**. For about an hour on 2026-10-07 that looked like a startup hang right after `<RI> Input initialized.`, until the window title gave it away. The dialog is a standard player option, and this project has it set to `Enabled` (`PlayerSettings.displayResolutionDialog`, printed by the audit), so real players see it on launch, as the original team configured. Why many *automated* launches skipped it is not known. `Tools/press-play.ps1` presses Play! the way a player would, by sending the button's command to the dialog (no mouse, keyboard or focus needed), and the script then requires a normal PASS. `--screenshots` saves the game's own rendered frames (launcher, arena, a 360° pan, panels) to `<out>/screenshots`.
- **Definition of "verified" before merging upward:**
  - `feature/*` → `revival/phase-0-1-bringup`: `checks` green **and** `Tools/verify-local.sh --windowed` prints `VERIFIED` on a **fresh clone of the exact commit being merged** (merge with `gh pr merge --merge --match-head-commit <sha>`, so nothing else slips in).
  - `revival/phase-0-1-bringup` → `dev`: all of the above **and** the milestone's own end-to-end proof (M1: opens/compiles/scenes clean; M2: two clients in one Photon room, damage lands both ways).
  - `dev` → `master`: `dev` has been exercised by real play (closed playtest, M3) with no open blockers.
- **Mechanics:** open a PR (`gh pr create`), wait for `checks`, merge with a **merge commit** (`gh pr merge --merge`). Not squash or rebase: this file cites individual commit SHAs, and those must stay reachable. Keep feature branches after merging, for the same reason. A direct `git push` to `dev` or `master` is now rejected by GitHub; that is intentional.
